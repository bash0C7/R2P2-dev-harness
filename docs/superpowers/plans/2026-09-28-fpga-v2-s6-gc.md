## 0. 決めたこと (要約)

1. **GC が走るのは確保の所だけ (C と同じ)。** firmware の Integer の番地を守るのは C と同じ **arena**。
   - `mrb_vm_exec` と `mrb_funcall_with_block` の `ai` を写す
   - firmware のフレームは C の関数のフレームとして扱う
   - C から VM を点けたフレームは C と同じ `CINFO_SKIP` にする
   - firmware の値の持ち方 (Integer の番地) は変えない (§3)
2. **回路の命令と primitive は、途中で firmware に落ちない。**
   - 始める前に速い道の条件 (負債、free_heaps、arena の空き、stress の数、shrink) を全部確かめる
   - 足りなければ命令ごと `__fpga_op_X` の罠にする (§5.1)
3. **順は「止まる GC → incremental」を S6 の中で。**
   - GC の本体 (状態機械、gray stack、sweep、write barrier の中身) は最初から gc.c のとおり写す
   - 駆動だけを `run_to_root` (1 step で 1 周、D20) で始め、S6-6 で step の上限を写して D20 / D23 を消す
   - generational (D21) は S6 の完了に入れず、別の段 S6g にする (§4)
4. **確保の速い道:** 回路は枠 (RVALUE) の freelist から外す所まで。可変長 (estalloc) が要る命令は、その命令ごと罠にする (§5)
5. **estalloc は firmware に 1 つだけ書き、CRuby でも同じ file を読む** (像の道具と Fiddle の検査が使う)。C の .so と、BPOOL_TOP からの差で比べる (§6)
6. **像は pool と heap page を持つ。**
   - 書き換わる物 (組み込みのクラス、metaclass、Kernel の iclass、それらの表) は heap page の枠と estalloc のブロックに置く
   - firmware の Proc と irep は ROM の RED (§7)
7. **stress は N = 1 (C の MRB_GC_STRESS と同じ) を起動と programs に。**
   - fuzz と accept の一部は、1 回の GC の命令数を測ってから N を式で決める。N には上限を置く
   - ref の高速化 (別の agent が進めている) を S6-5 の前提にする (§9)

## 3. 最大の課題: firmware の Integer の番地と GC

firmware は物の番地を Integer で持つ (`__fpga_addr(v)`、`__fpga_ld32(p + C_SUPER)` の結果、`__fpga_slot` の戻り値)。
Integer は即値なので、`mark_context_stack` が firmware のフレームのレジスタを読んでも印を付けない。GC が走った時に、firmware が Integer でだけ持っている物は解放され得る。

### 3.1 C で GC が走る所

- `mrb_obj_alloc_core`:
  - `gc_debt` が正なら `mrb_incremental_gc`
  - free_heaps が空で余りがあれば `mrb_full_gc`
  - `MRB_GC_STRESS` なら毎回 `mrb_full_gc`
- `mrb_realloc_simple`:
  - 新しい確保 (`p == NULL`) で `malloc_increase` が閾値を超えたら `mrb_incremental_gc`
  - 確保に失敗したら緊急の `mrb_full_gc` か `incremental_gc_finish`
- `GC.start` (`gc_start` → `mrb_full_gc`) と、mruby-task の scheduler の `mrb_gc_step` (S7)
- 以上だけ。命令の切れ目や割り込みでは走らない。**確保 (と GC.start) の呼び出しが GC の safe point** で、その間は GC から見て一続き

### 3.2 C は C の局所変数をどう守っているか

- C の関数の局所変数 (`struct RArray *a`、`mrb_value v`) も GC の根ではない。守りは 2 つだけ:
  1. **arena:** `mrb_obj_alloc_core` は作った物を必ず `gc_protect` で arena に積む。arena は root_scan が印を付ける。
     arena を戻すのは次の所だけ:
     - vm.c (命令ごと、cfunc の epilogue、`mrb_funcall_with_block` の出口)
     - C の関数が自分で書いた `mrb_gc_arena_save` / `restore`
     - `mrb_init_core` の `DONE`

     だから C の関数が作った物は、その関数が VM に戻るまで生きている
  2. **到達:** 前からある物は、根 (レジスタ、グローバル、クラスの木、arena) から辿れる限り生きている。
     C の関数が物を根から外してから確保する所は、C 自身が `mrb_gc_protect` などで守っている (gc.rb の assert の多くはこの不具合の再発止め)
- firmware は C の写しなので、**C と同じ所で確保し、同じ順で根を書き換えれば、同じ 2 つの守りがそのまま効く。** 足りないのは arena の仕組みだけ

### 3.3 候補

| 案 | 中身 | 良い所 | 悪い所 | 判定 |
|---|---|---|---|---|
| **A. arena と `mrb_vm_exec` の活性化を写す** | 回路が `ai` を C と同じ所で save / restore。firmware のフレームは C の関数のフレームで、その中の命令では restore しない。firmware から Ruby を点ける所で新しい活性化 (`CINFO_SKIP`) | C と同じ不変条件。firmware の書き直しが要らない。gc.rb の arena の assert (GETIDX、ENTER ほか 14 本) がそのまま物差しになる | firmware が C と違う順で書いた所は守られない。firmware の命令が作る一時の物で arena が C より伸びる (D83) | **選ぶ** |
| B. firmware のフレームが ci に無い時だけ GC | 確保の所で firmware のフレームが積まれていれば GC を延ばす | Integer を見なくてよい | 起動の `__fpga_boot` と `__fpga_run` がいつも一番下にある (§1.4)。firmware からの callback の中でも GC できない。GC の時期が C と違う | 捨てる (一度も GC できない) |
| C. firmware の値を mrb_value で持つ | 物の番地を `__fpga_obj` の値でレジスタに置く | GC が firmware のレジスタを正確に辿れる | firmware 約 17,000 行の書き直し。中身の buffer の番地は Integer のまま残る。C より保守的で写しから離れる | 捨てる |
| D. firmware のフレームを保守的に走査 | firmware のレジスタの Integer が枠を指せば印を付ける | 変更が小さい | 86921ce の「保守的なスタックの根」と同じ自前の設計 | 捨てる (§3.6 の検査にだけ使う) |
| E. GC を ref (CRuby) で走らせる | GC を回路の機能にする | 速い | 設計 §1 の分け方 (gc.c は firmware) に反する | 捨てる |

**A を選ぶ理由:**
- C が C の局所変数を守るやり方そのものを写す (設計しない、写す)
- firmware は C の写しなので、C が守っている所は firmware でも守られる。守られない所 (写しの順の違い) は C でも不具合になる種類で、stress と解放後の使用の検査 (§3.6) で見つけられる
- mruby 自身の GC の不具合の再発止め (test/t/gc.rb の 25 本) が、この仕組みの正しさを直接測る

### 3.4 回路の規則 (ref に書く。V3 の回路も同じ)

**firmware の判定は irep の番地で:** ci の Proc の irep が像の中 (ROM の irep、`irep < heap_start`) なら firmware のフレーム。
- Proc の番地では判定しない。firmware が作る Proc は無い (firmware_test が firmware に LAMBDA / BLOCK / METHOD の命令が無いことを固定する) ので、ROM の irep を持つ Proc は像の中の RED の Proc だけ
- 罠のフレーム (D10、CONT_* が NONE 以外) と起動のフレームも firmware のフレーム

**cci の使い分け (C のとおり):**

| 値 | 使う所 | 写し元 |
|---|---|---|
| `CINFO_NONE` | 普通の呼び出し | vm.c `OP_SEND` |
| `CINFO_SKIP` | C から VM を点けたフレーム。活性化の始まり | vm.c `mrb_funcall_with_block` (irep の時に SKIP に替える)、`yield_with_attr`、`mrb_vm_run` の前の `cipush` |
| `CINFO_DIRECT` | C から呼んだ C の関数。**罠のフレームと起動のフレーム** (D11 のまま) | vm.c `mrb_funcall_with_block` の cipush |

**延長の語 `CI_AI` (D82):** `ai + 1` (0 は無し) と、戻りで protect するかの 1 bit を持つ。

- 持つのは、C の `mrb_funcall_with_block` / `yield_with_attr` に当たる呼び出しで積んだフレームだけ。罠のフレーム、起動のフレーム、普通の呼び出しは 0
- 回路の `ai` レジスタ (ref の `@ai`、ref_test の `CRUBY_STATE` に足す) は、今の活性化 (一番近い SKIP のフレーム) の ai の cache。巻き戻しの後は記憶から読み直す

| 規則 | 何をするか | 写し元 |
|---|---|---|
| R1 活性化の始まり | **ci の proc を置く所** (ref の `write_ci` と `vm_call_proc`) で、1 つ下の ci が firmware のフレームで、置く proc が firmware でなければ:<br>・cci を `CINFO_SKIP` にする<br>・`CI_AI` に今の `arena_idx` を置く<br>・`ai` をそれにする<br>当たるのは `__fpga_sendv` / `__fpga_invoke` / `__fpga_run`、firmware の中の SEND、BLKCALL (yield)、Proc#call (ROM の Proc#call の中の OP_CALL が ci の proc を差し替える所) | `mrb_funcall_with_block` の save と `ci->cci = CINFO_SKIP`、`yield_with_attr`、`mrb_vm_exec` の入口の `ai` |
| R1' C から C の関数を名前で呼ぶ | firmware のフレームから、名前が `__fpga_` で始まらないメソッド (動的な送り: `v.to_s`、`__fpga_sendv` の先) が firmware の def に当たった時は、C の `mrb_funcall` で C の関数を呼ぶ形。cci は `CINFO_DIRECT`、`CI_AI` を置く (protect の bit は 1)。`ai` は替えない (新しい mrb_vm_exec は点かない)。firmware の helper (`__fpga_` の名前、D14) の呼び出しは C の関数の直接の呼び出しで、何もしない | `mrb_funcall_with_block` の cfunc の道 |
| R2 命令の restore | 像の外のフレームで、ops.tsv の「restore の時点」の列 (S9、§5.4) に当たる時に `arena_idx = ai`。罠で終えた命令は、罠から戻った所で同じにする。**firmware のフレームの中の命令では restore しない** (C の関数の中に restore は無い) | vm.c の各 `CASE` の `mrb_gc_arena_restore(mrb, ai)` |
| R3 C の関数の後 | 像の外のフレームが呼んだ firmware の**メソッド** (CONT_NONE、`CI_AI` が 0) が戻った時、値を R[a] に書いてから `mrb_gc_arena_shrink(ai)`。shrink が realloc の条件 (`ai < arena_capa / 4` で capa が縮む) に当たる時は、戻りの命令ごと罠 (§5.1)。罠のフレームが戻った時は R3 でなく R2 (その命令の restore だけ) | vm.c `L_SENDB` の cfunc epilogue (3852)、`mrb_gc_arena_shrink` |
| R4 活性化の終わり | `CI_AI` が 0 でないフレームが戻る時:<br>・`arena_idx = CI_AI - 1` にする<br>・protect の bit が 1 (funcall) なら戻り値を `gc_protect` する。yield と Proc#call は protect しない<br>・`ai` を下の活性化のものに戻す<br>arena には「いつも 1 つ空き」(§5.1) があるので、protect は確保を要らない | vm.c L_RETURN の `acc == CINFO_SKIP \|\| acc == CINFO_DIRECT` の restore、`mrb_funcall_with_block` の restore と `mrb_gc_protect(val)` |
| R5 例外の巻き戻し | firmware は巻き戻す前に、捨てる各 ci の env を閉じる (vm.c `cipop` の `mrb_env_unshare`、firmware の写し。確保する)。その後に `__fpga_unwind` / `__fpga_unwind_ret` を呼ぶ。primitive は確保しない。着いたフレームが像の外なら、その活性化の ai に `arena_idx` を戻し、`ai` を付け直す。着いたのが firmware のフレームなら何もしない (C の MRB_TRY の側の C の関数が自分で戻す。例: error.c `mrb_protect_error`) | `mrb_vm_exec` の `RETRY_TRY_BLOCK` の restore |
| R6 回路が確保する時 | 回路 (ref の Ruby の局所変数) が物の値を持ったまま確保してはいけない。値はスタックか ci か arena に置いてから確保する | vm.c の `OP_ENTER` の直し (gc.rb「OP_ENTER keeps the block alive」) |

- 起動: `__fpga_boot` は戻らない。init.c の `mrb_init_core` の `DONE` (`mrb_gc_arena_restore(mrb, 0)`) を、firmware の起動の各 init の後と mrblib を読んだ後に写す (M3)
- firmware のメソッドから `__fpga_` の helper を呼ぶのは C の関数の直接の呼び出しで、arena に何もしない

### 3.5 firmware の側の関所

- **C の関数が arena を触る所は firmware も同じく触る。** 数える呼び出しは次のとおり:
  - `mrb_gc_arena_save` / `mrb_gc_arena_restore`
  - `mrb_gc_protect`、`mrb_gc_register` / `mrb_gc_unregister`
  - `mrb_field_write_barrier` (`_value` も)、`mrb_write_barrier`
  - `mrb_free` / `mrb_realloc`
- **一覧は生成する (S2):**
  - `fpga/v2/inventory/gc_calls.tsv` は手で書かない。`c_calls.rb` の呼び出しの木を推移閉包で辿って作る。C の関数 f が直接か static な helper を通して上の関数を呼べば、f の行にその数を出す
  - firmware の def は `# C:` の写し元の行と照らす。`# C: none (Dnn)` の def も、中で呼ぶ firmware の def を辿って数える
  - 足りない行は「足りない一覧」として同じ生成物に出し、inventory_test が commit と照らす。S6-3 / S6-4 / S6-6 で空にする
- **GC の中では確保しない。**
  - gc.rb の def の irep に物を作る命令 (ARRAY 系、STRING、HASH、LAMBDA / BLOCK / METHOD、RANGE、STRCAT、INTERN) があれば firmware_test が fail にする
  - ref は `collecting` の間の確保を `Ref::Error` にする。C には RData の dfree の中の確保があり得るが、firmware に RData は無いので、確保は不具合の印
- `__fpga_alloc` と `__fpga_slot` は S6-2 で無くす (firmware_test: 名前が 0 か所)
- firmware に LAMBDA / BLOCK / METHOD の命令が無い (§3.4 の判定の前提。firmware_test)

### 3.6 危険の分析: レジスタの Integer が動いた / 解放された物を指す

mruby の GC は物を動かさない。動くのは estalloc の `est_realloc` の中身 (ALLOC_AND_COPY) だけ。危ないのは次の型:

| 型 | 例 | C では | firmware での手当て | 見つけ方 |
|---|---|---|---|---|
| (a) 作ったばかりの物を Integer で持つ | `o = mrb_obj_alloc(...)` の後に別の確保 | arena | R1〜R4 と `mrb_obj_alloc_core` の `gc_protect` | gc.rb の arena の assert、stress |
| (b) 前からある物を、根から外した後も Integer で使う | 配列から pop した要素、表から消した行の値 | C も同じ危険。写し元は `mrb_gc_protect` か順で守る | 写し元と同じ順と protect (§3.5 の関所) | stress (N = 1)、下の「解放後の使用の検査」、独立の到達の検査 (§9.4) |
| (c) 中身の buffer の番地を持ったまま同じ物を伸ばす | `ptr = ld32(ary + A_PTR)` の後に push | C も読み直す (`ARY_PTR`) | 写し元どおり読み直す | stress の estalloc の埋め (D87) |
| (d) 罠の続きの語が値を持つ | CI_CA / CN / CSYM / CRET / CDST | — | 数と symbol だけで物を持たない (D11)。layout の注釈に書き、ref_test で確かめる | ref_test |
| (e) 回路が CRuby の局所変数で値を持って確保 | ref の `enter` の `regs` と `blk`、`alloc_array` の `values` | vm.c は OP_ENTER で直した | R6。確保する回路の命令と primitive の一覧を ref の頭に書く。一覧の外の primitive が確保したら ref の assert で Error | gc.rb の OP_ENTER の assert、stress |
| (f) method cache と decode の cache | クラスが解放され、枠が別のクラスに使い回される | `obj_free` の `mrb_mc_clear_by_class` | 回路の method cache を消す (D90)。decode の cache は iseq が像の中なので影響無し。V4 で `.mrb` を pool に読むようになったら、irep の解放で消す | stress、programs |
| (g) スタックの上の方 | `mark_context_stack` が top の ci の `stack + nregs` から上を nil で消す | 同じ | firmware のフレームの nregs は firmware の irep の値で、C の cfunc より大きい。罠の窓 (D11) は罠のフレームの中 | ref_test |
| (h) 例外が活性化をまたぐ | firmware の rescue で止まる、`__fpga_unwind` | MRB_TRY / MRB_CATCH と `ai` | R5 | exceptions の program と exception.rb を stress で |

**解放後の使用の検査 (ref の stress の中、意味は変えない):** 解放した枠を -1 で埋めても、枠は LIFO で使い回されるので、次の確保で上書きされて埋めが消える。そこで値でなく**レジスタに印を付ける**:
- 印を付ける: sweep が枠を解放した時、その番地と同じ Integer を持つ firmware のフレームのレジスタ
- 印を運ぶ: MOVE で写した先のレジスタにも付ける
- 印を消す: そのレジスタに別の値を書いた時
- 印のあるレジスタが `__fpga_ld*` / `__fpga_st*` / `__fpga_obj` / `__fpga_copy` の番地の引数に使われたら `Ref::Error` (解放した物を使った)
- 死んだ局所変数は、使われない限り Error にならない

## 4. 止まる GC か incremental か: 順の決定

- **決める:**
  - GC の本体 (gc.c の状態機械、gray stack と溢れた時の走査、final_marking_phase、sweep、write barrier の中身) は S6-4 で全部写す
  - 駆動だけを `run_incremental(..., run_to_root = TRUE)` にする (D20)
  - S6-6 で `incremental_gc_step` の上限と、barrier を呼ぶ所の全部を入れて、D20 / D23 を消す
  - generational (D21) は **S6 の完了に入れない**。別の段 S6g として S7 の後か並べて行う
- **理由:**
  - 1 周で終える駆動では、変更の側 (mutator) が走る時はいつも state が ROOT で、生きている物は全部白い。
    barrier (`mrb_field_write_barrier` / `mrb_write_barrier`) は黒い物を見ないと何もしないので、中身を写しても働かない。だから中身は最初から写してよく、D22 (中は空) は要らない
  - barrier を呼ぶ所は回路 (ref) の命令にもある (SETUPVAR と、容量の中の ARYPUSH / ARYCAT。§5.1)。ref は V3 の回路の仕様なので、V3 の前 (S6 の中) に決める
  - 1 周で終える段を先に置くのは、根と sweep の誤りと、barrier の抜けを分けて見つけるため
  - generational は barrier と page の old の扱いの上に載る別の仕組みで、S6 の範囲を広げすぎる (レビュー)
- **incremental を V3e に戻す条件 (客観的に):** 次のどれかで、D20 / D23 の行を「予定 V3e」のまま残して S7 へ進む (記録に書く)。V3 に入る条件 (計画本体) は変えない
  - S6-6 の incremental の stress (§9.2) が 3 回の直しの commit の後も host と違う
  - incremental の stress の集合の実行の時間が、§9.2 の予算の 2 倍を超える

## 5. 確保の速い道 (回路、ref.rb) と罠、負債、arena

### 5.1 回路がすること (設計 §6 の「確保」の行を具体に)

**決まり: 回路の命令と primitive は、途中で firmware に落ちない。**
- 始める前に、その命令が要る条件を全部確かめ、1 つでも足りなければ、何も書かずに命令ごと罠 `__fpga_op_<命令>` (primitive なら primitive ごと、firmware の写しの def) にする
- 罠の先の firmware は、C のとおり 1 から全部を行う (`gc_debt++` と stress の数も firmware の写しが数える。回路は数えない)
- ref は「罠に落ちた命令が記憶を書いていない」を ref_test で確かめる

**枠の確保 (`mrb_obj_alloc_core` の後ろ半分):** 記憶の中の `mrb_gc` を読み書きする (S2b の決まり: 状態は記憶に)。

1. **条件を確かめる** (どれかが外れたら命令ごと罠):
   - `gc_debt + 1 <= 0`
   - `free_heaps != 0`
   - `arena_idx + 1 < arena_capa` (**arena はいつも 1 つ空き**。積んだ後も 1 つ空く。R4 の protect が確保なしで積めるため。D91)
   - stress の数が N に達していない
   - その命令が枠を 2 つ以上作るなら、その数だけ
2. `gc_debt += 1`、stress の数を +1
3. `p = free_heaps->freelist`、`free_heaps->freelist = p->next`、空なら `free_heaps = free_heaps->free_next`
4. `live += 1`、`arena[arena_idx++] = p`
5. 枠 64 バイトを 0 で埋め、`tt` と `c` と色 (`current_white_part`) を書く。
   OBJECT の `MRB_FL_OBJ_SHAPED` (iv の shape) は FPGA の iv 表 (D06) に無い。S6-0 で layout を見て、D06 の行に書き足す

**回路が確保する命令と primitive (この一覧の外は確保しない。ref の assert):**

| 命令 / primitive | 回路でする時 | 罠にする時 |
|---|---|---|
| ARRAY / ARRAY2 | 要素 0 個 (`ary_new_capa(0)` は malloc しない。枠 1 つ) | 要素が 1 つ以上 (中身の malloc) |
| ENTER | rest が空 (空の配列の枠 1 つ)、rest が無い | rest が空でない |
| ARYPUSH / ARYCAT | 容量の中の追加 (確保しない。barrier `mrb_write_barrier(ary)` を呼ぶ) | 容量を越える (`ary_expand_capa` の realloc)、ARYCAT の nil (複製) |
| SETUPVAR | 確保しない。barrier `mrb_write_barrier(env)` を呼ぶ | — |
| RETURN 系 | 閉じる env が無く、R3 の shrink が realloc にならない | cipop で env を閉じる (`mrb_env_unshare` の malloc)、shrink が realloc になる |
| `__fpga_obj_alloc(tt, cls)` | 上の 1〜5 | primitive ごと firmware の `mrb_obj_alloc_core` の写し |
| `__fpga_run(irep, self)` | 確保しない。Proc は firmware が先に `mrb_proc_new` で作って渡す (load.c `mrb_load_exec` のとおり) | — |
| `__fpga_unwind` / `__fpga_unwind_ret` | 確保しない。env は firmware が先に閉じる (R5) | — |

- SETIV と DEF は ref では罠 (firmware) なので、その barrier は firmware の写しが呼ぶ
- **可変長:** estalloc (`est_malloc`) は S6 では firmware だけが持つ。回路に TLSF を持たせるかは V3 で測って決める (設計 §9 に候補として書く)
- **負債の勘定:**
  - `gc_debt` は枠の確保で +1、`incremental_gc_step` の仕事で減る
  - 1 周の終わりに `-credit` (`incremental_gc_run`、`mrb_full_gc` の式)
  - `malloc_increase` は `mrb_realloc_simple` の中 (firmware) だけで数える

### 5.2 罠 (firmware の入口)

| 罠 | firmware の def (`# C:`) |
|---|---|
| `__fpga_obj_alloc` の落ち先 | gc.c `mrb_obj_alloc_core` |
| `__fpga_op_ARRAY` / `ARRAY2` / `ENTER` / `ARYPUSH` / `ARYCAT` / `return` | vm.c の各 `CASE` と、そこから呼ぶ `ary_new_from_regs`、`vm_op_enter`、`mrb_ary_push`、`cipop`、`mrb_env_unshare`、`mrb_gc_arena_shrink` |

### 5.3 資源の見込み (設計 §9 に足す、S6-5)

| 項目 | 見込み | 根拠 |
|---|---|---|
| サイクル (当たり) | 30〜40 | `mrb_gc` の語を 6 つ読み書き (data cache に当たれば 1〜2 cycle)、枠の 16 語を 0 (SDRAM の burst 2 回)、arena に 1 語 |

### 5.4 ops.tsv の「restore の時点」の列 (S9)

ops.tsv の arena の列は、restore が効く時点の違う 3 種を混ぜている。`vm_table.rb` が列「restore の時点」を足し、ref はその列を読む (手で表を書かない):

| 種 | 意味 | 例 |
|---|---|---|
| `case` | CASE の本文の行。命令を終えた時にいつも | ARRAY、STRING、HASH、CLASS、DEF、RETURN の L_RETURN |
| `cfunc` | `L_SENDB` の cfunc の epilogue。呼んだのが C の関数 (firmware のメソッド) だった時だけ (R3) | SEND 系、SUPER、演算の送り |
| `funcall` | static な helper の中の save / restore。helper が `mrb_funcall` した時だけ (その helper の写しが firmware なら firmware の中で、回路の道なら回路で) | GETIDX GETIDX0 SETIDX DIV ADDILV SUBILV の `vm_op_*` |

## 6. estalloc の写しと Fiddle の検査

- **1 つの source:** `fpga/firmware/estalloc.rb` (mruby ソースコード、`# C: estalloc.c <関数>`)。firmware の像に入り、ref の上で走る
- **CRuby でも同じ file を読む:** `tools/fpga/v2/est_host.rb` (Ruby コード)
  - `__fpga_ld8` / `st8` / `ld32` / `st32` / `and` / `or` / `xor` / `shl` / `shr` を持つ名前空間の中で estalloc.rb を読む。
    `Module.new` の `module_eval` を使い、`class Object` は名前空間の中の新しいクラスになる
  - 記憶は binary の String
  - 使う所は 2 つ: image.rb が pool を作る (§7)、estalloc_test が C と比べる
- **pool の状態の置き場 (M2):** heap.c の static (`picorb_heap_estalloc`、`picorb_heap_start`、`picorb_heap_end`) は、IMG の像だけの欄 (D18) に置く
- **比べ方** (`tools/fpga/v2/estalloc_test.rb`、`rake test:fpga` に入れる):
  - estalloc.c を `cc -shared -fPIC -O0 -DESTALLOC_ALIGNMENT=8` で一時の dir に build し、Fiddle で `est_init` / `est_malloc` / `est_calloc` / `est_realloc` / `est_free` / `est_permalloc` / `est_usable_size` / `est_take_statistics` を呼ぶ
  - 同じ操作の列を est_host (32bit の形) に与える。操作の列は seed つきの乱数で、次の形を混ぜる:
    - 大きさ 0〜300 が多く、ときどき 1〜70,000
    - realloc は伸ばすと縮める。free は生きているものから選ぶ
    - permalloc は少し
    - pool が尽きて NULL になる所まで回す列も入れる
  - **比べるもの:**
    - 各操作の戻りを `BPOOL_TOP` からの差 (NULL は nil)
    - `est_usable_size`
    - `est_take_statistics` の 5 つ。total は `total - POOL_HEADER_SIZE` で比べる。frag は uint32 の wrap (C の型のまま `& 0xFFFFFFFF`) で比べる (M1)
  - C の pool の大きさを P とすると、est_host の pool は `P - POOL_HEADER_SIZE(64bit) + POOL_HEADER_SIZE(32bit)` にして、使える領域の大きさをそろえる
  - ref の上の firmware も短い列 (200 操作) で est_host と比べる。C、CRuby、ref の 3 者が一致すること
- **32bit と 64bit の違い (D25 を書き直す):**
  - 64bit の CRuby は 32bit の .so を読めない。この環境の gcc には `-m32` が無い (確かめた)
  - 違いは次の 3 つ:
    - `FREE_BLOCK` の大きさ (64bit は 32、32bit は 16)
    - `top_adrs` の位置 (block の終わりから 8 と 4)
    - `POOL_HEADER_SIZE`
  - `USED_BLOCK` はどちらも 8、`ESTALLOC_IGNORE_LSBS` と最小のブロックはどちらも 32 (ALIGNMENT 8)
  - なので `calc_index` と分割と結合の判断は同じで、戻りの番地は BPOOL_TOP からの差で一致するはず。一致しない列が出たら、この議論が誤りなので段を止める
  - 見られないのは `-m32` の build そのもので、upstream の `make test_8_24_32bit` に任せる
- **写さないもの:** `ESTALLOC_DEBUG` の検査 (解放のたびの heap の走査、二重の free の検出)。組み込みの build は DEBUG 無し。
  stress の時の埋め (0xaa / 0xff) だけは D87 で入れる

## 8. task の scheduler (S7 との境)

- root_scan_phase と final_marking_phase は `mrb_task_mark_all` を呼ぶ (`MRB_USE_TASK_SCHEDULER`)。S6-4 は task.c の `mrb_task_mark_all` のうち、次の所までを写す:
  - main_task が NULL
  - queues[0..3] が全部 NULL なら早く return する
  - S6 には task が無いので、この写しで正しい
- **S7 への申し送り** (S7 の担当が計画本体の S7 の節に足す):
  - 残り (各 task の `mrb_context` の stack と ci の印) を同じ def に足す
  - `execute_task` (task.c) の arena の save / restore (`mrb_protect_error` の前後) を §3.5 の関所で写す
  - **task を再開する時は、その task の活性化の `CI_AI` を今の `arena_idx` に書き直す** (止めた時の arena の位置は、他の task が動いた後では意味が無い)

### 9.2 stress の N と範囲

- **前提:** ref の高速化 (別の agent が進めている) が S6-5 の前に入っていること。入っていなければ S6-5 は待つか、下の N の上限で範囲を削る (記録に書く)
- **1 回の GC の重さ:** 起動の後に生きている枠は約 400、pool の中の表の行は数千。gc.rb (firmware) の印と sweep で 1 回 **約 10 万命令** と見る (楽観しない側)。
  スタックの nil の埋め (65,536 値) は primitive `__fpga_fill` で 1 命令にする (D81)。**S6-5 の最初に、起動の直後の `GC.start` の命令の数 C_gc を測って N を決め直す**
- **N の決め方:**
  - 回す集合の確保の数を E (枠と realloc の合計、stat で数える)、許す時間を B 秒、ref の速さを V 命令/秒とする
  - N は、`E × C_gc / N ≤ B × V` を満たす一番小さい 2 の冪
  - ただし N は下の上限を超えない。超えるなら範囲を削る (file を減らす)。ref が速くなったら N を小さくする (記録に書く)
- **stat `gc` の下限:** stress で回した各 program / fuzz の各本 / accept の各 file の stat `gc` が、`max(1, E / N の半分)` 以上 (stress が効いていない file を見つける)

| 集合 | N | N の上限 | B | E の見込み | 中身 |
|---|---|---|---|---|---|
| 起動 | 1 (C の MRB_GC_STRESS と同じ) | 1 | 段の終わりに 1 回の長い仕事 (nohup で切り離し、かかった時間を記録) | 約 1,500 | 空のプログラム 1 本。firmware の loader、クラスの定義、mrblib の読み込みの全部 |
| programs 9 本 (起動の後から) | 1 | 1 | 30 分 | 計 約 3,000 | 全部 |
| fuzz | 式 | 64 | 60 分 | seed 1 の 100 本で 約 20,000 | seed 1 |
| accept の一部 | 式 (file ごと) | 256 | 60 分 | file ごとに stat で測る | gc、hash、string、exception、proc、bs_block、class、module、methods、symbol、range。array は深い join (step の上限 3B) があるので外す |
| incremental の stress (S6-6) | 確保ごとに 1 step (上限 `step_limit` 16) | — | 60 分 | 同じ | programs 9 本と fuzz seed 1 |

- stress の像は `gc_stress` の語 (D87) を立てる。ref は `Ref.new(image, ...)` の引数で受ける。
  入口は `rake fpga:v2:stress` (programs と起動) と、`fpga:v2:fuzz` / `fpga:v2:accept` の引数。環境変数にはしない
- stress の時は gc.c の `MRB_GC_STRESS` と `MRB_DEBUG` の道も写して入れる:
  - 解放した枠を -1 で埋めて白くする (`obj_free` の末尾)
  - `add_gray_list` の tt の検査
  - estalloc の 0xaa / 0xff の埋め (D87)
  - §3.6 の解放後の使用の検査 (レジスタの印)
- incremental の stress (S6-6) では、ref が MARK の各 step の境で「黒い物から白い物への辺が無い」を確かめる (§9.4 の表で辺を辿る)

### 9.3 小さいヒープ

- **普通:** pool は像の後ろ全部 (約 30 MB)。GC は負債で走る (`GC_STEP_SIZE` 1024 が credit の下限なので、1,000 個ほど確保するたびに 1 周)
- **小さい:** pool は、起動の後の estalloc の used (S6-2 で測る) の 2〜3 倍にする。
  heap page を足す道と、`mrb_full_gc` で取り戻す道を踏ませる。値は測って記録に書く
- **回す file:** accept の範囲内の全部 (S6-4 と S6-6 の完了の時)。途中の段は §9.2 の accept の一部と同じ集合
- **比べ方:** host とは、accept の合格の集合だけを比べる (host の HEAP_SIZE は変えない)。小さいヒープの ref で出た NoMemoryError は不合格に数える
- **完了の条件:**
  - programs と fuzz seed 1 が、小さいヒープで stat `gc` > 0、`gc_freed` > 0、`heap_page_free` (空の page を返した数) > 0
  - accept の合格の集合が、普通と小さいで同じ

### 9.4 独立の到達の検査 (gc_test、Ruby コード)

- **根と辺の表は gc.c から作る:** `root_scan_phase` の根の並びと、`gc_mark_children` の tt ごとの子を表 (`tools/fpga/v2/gc_edges.rb`、各行に `# C: src/gc.c <関数> <case>`) にする。
  辿る実装だけを CRuby で独立に書く (gc.rb の写しを使わない)
- stress の各 GC の後に、ref が根 (mrb_state の根の欄、arena、`mrb_context` の stack と ci) から記憶を辿る
- **必須 (fail にする):** 辿れる物に FREE が無い
- **差を出すだけ:** 使っている枠 = 辿れる物 ∪ arena から辿れる物 (1 周で終える駆動の時)。多い分 (漏れ) は数を記録に出し、fail にしない
- S6-6 (incremental): MARK の各 step の境で、黒い物から白い物への辺が無い (§9.2)
- S6g (generational): minor の後に、old の物から印の無い若い物への辺が無い

## 12. 危険と、レビューで突かれそうな所の自己点検

| 突かれそうな所 | 答え | 残る弱さ |
|---|---|---|
| 「arena を写せば安全」は、firmware が C と同じ順で書かれている前提に頼る | 関所は 4 つ:<br>・§3.5 の生成した数の検査<br>・stress N = 1<br>・解放後の使用の検査 (レジスタの印)<br>・独立の到達の検査 | 呼ぶ数が合っていても置き場所が違う場合は、数の検査では見えない。stress が確保の所を全部踏まない限り見逃す |
| firmware の命令が C に無い物を作り、arena が伸びる (D83) | C の関数が戻れば縮む。`arena_max` を測る | firmware の長い loop (10,000 段の join など) で arena と pool が大きく伸びる。小さいヒープで NoMemoryError になれば、写し元の C が arena を戻す所を見て、違いを D に足す |
| firmware のフレームの判定 | irep の番地 (ROM の irep) で。firmware に LAMBDA / BLOCK / METHOD が無いことを固定 | V4 で `.mrb` を pool に読んでも、読んだ irep は像の外なので正しいまま。firmware を pool に置く日は来ない前提 |
| 回路が途中で firmware に落ちる | 「始める前に全部確かめる」決まりと、確保する命令の一覧、罠の後に記憶を書いていないことの ref_test | 条件の数え漏れ (枠を 2 つ作る命令など) は stress で見つける |
| 1 周で終える駆動は barrier の抜けを隠す | S6-6 を S6 の完了に置き、barrier を呼ぶ所の関所を S6-0 から生成して数える。MARK の step の境で黒→白の辺を検査 | S6-6 の stress の範囲 (programs と fuzz seed 1) で踏まない barrier は残り得る |

| estalloc を 64bit で比べて 32bit を保証したことになるか | §6 の 3 つの違いを列挙し、戻りの差の一致で確かめる。一致しなければ段を止める | `-m32` の build を回せない。sizeof に依る分岐を見落としていれば見えない |
| image.rb が add_heap を CRuby で写す (2 つ目の写し) | 小さい (枠の freelist だけ)。image_test と、S6-4 の起動の直後の GC と到達の検査で確かめる | 写しがずれると、起動の直後だけの誤りになる |
| S7 と layout の番号がぶつかる | S6-0 で `mrb_task_state` の語も取っておく | S7 が mruby.h と違う欄を要ると、また付け直す |
| スタックの nil の埋めが 1 MB (65,536 値) で重い | ref は `__fpga_fill` で 1 命令。回路は SDRAM に 26 万語を書く (約 2.6 ms、100 MHz) | 確定した短い遅延 (issue #4) には重い。high-water の印で縮めるのは V3 で (新しい D になる) |
| シンボルの GC を写さない (D89) | D07 の表の形と結びついている。test/t の 2 本は解放しないでも通る | 65,536 を超えるシンボルを作るプログラムで止まる (host は止まらない) |

| 可変長の命令を全部罠にすると ref が遅くなる | 起動の命令が増える (見込み +10〜20%)。記録に書く | 回路の TLSF を V3 で決めるまで、ref の時間の見込みが悪くなる |
