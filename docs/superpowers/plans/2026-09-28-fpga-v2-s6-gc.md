- 違い: [乖離表](../../fpga-v2-deviations.md)。この段が新しく使う番号は **D80〜D99** (予約)。既にある S6 の行 D20〜D26 と、S6 で消す D61 / D63 もここで扱う

## 0. 決めたこと (要約)

1. **GC が走るのは確保の所だけ (C と同じ)。** firmware の Integer の番地を守るのは C と同じ **arena** で、`mrb_vm_exec` の `ai` を写す。
   firmware のフレームは C の関数のフレームとして扱う (D41 と同じ見方)。firmware の値の持ち方 (Integer の番地) は変えない (§3)
2. **順は「止まる GC → incremental → generational」を S6 の中で。** GC の本体 (状態機械、gray stack、sweep、write barrier の中身) は最初から gc.c のとおり写し、
   駆動だけを `run_to_root` (1 step で 1 周、D20) で始める。S6-6 で step の上限を写して D20 / D23 を消し、S6-7 で generational を写して D21 を消す (§4)
3. **確保の速い道:** 回路は枠 (RVALUE) の freelist から外す所まで。可変長 (estalloc) が要る命令は、その命令ごと罠にする (§5)
4. **estalloc は firmware に 1 つだけ書き、CRuby でも同じ file を読む** (像の道具と Fiddle の検査が使う)。C の .so と、BPOOL_TOP からの差で比べる (§6)
5. **像は pool と heap page を持つ。** 組み込みのクラスなど書き換わる物は heap page の枠と estalloc のブロックに置き、firmware の Proc と irep は ROM の RED (§7)
6. **stress は N = 1 (C の MRB_GC_STRESS と同じ) を起動と programs に。** fuzz と accept の一部は、1 回の GC の命令数を測ってから N を式で決める (§9)

## 3. 最大の課題: firmware の Integer の番地と GC

firmware は物の番地を Integer で持つ (`__fpga_addr(v)`、`__fpga_ld32(p + C_SUPER)` の結果、`__fpga_slot` の戻り値)。
Integer は即値なので、`mark_context_stack` が firmware のフレームのレジスタを読んでも印を付けない。GC が走った時に、firmware が Integer でだけ持っている物は解放され得る。

### 3.1 C で GC が走る所

- `mrb_obj_alloc_core`:
  - `gc_debt` が正なら `mrb_incremental_gc`
  - free_heaps が空で余りがあれば `mrb_full_gc`
  - `MRB_GC_STRESS` なら毎回 `mrb_full_gc`
- `mrb_realloc_simple`:
  - 新しい確保 (`p == NULL`) で `malloc_increase` が閾値を超えたら `mrb_incremental_gc`
  - 確保に失敗したら緊急の `mrb_full_gc` か `incremental_gc_finish`
- `GC.start` (`gc_start` → `mrb_full_gc`) と、mruby-task の scheduler の `mrb_gc_step` (S7)
- 以上だけ。命令の切れ目や割り込みでは走らない。**確保 (と GC.start) の呼び出しが GC の safe point** で、その間は GC から見て一続き

### 3.2 C は C の局所変数をどう守っているか

- C の関数の局所変数 (`struct RArray *a`、`mrb_value v`) も GC の根ではない。守りは 2 つだけ:
  1. **arena:** `mrb_obj_alloc_core` は作った物を必ず `gc_protect` で arena に積む。arena は root_scan が印を付ける。
     arena を戻すのは vm.c (命令ごと、cfunc の epilogue、`mrb_funcall_with_block` の出口) と、C の関数が自分で書いた `mrb_gc_arena_save` / `restore` だけ。
     だから C の関数が作った物は、その関数が VM に戻るまで生きている
  2. **到達:** 前からある物は、根 (レジスタ、グローバル、クラスの木、arena) から辿れる限り生きている。
     C の関数が物を根から外してから確保する所は、C 自身が `mrb_gc_protect` などで守っている (gc.rb の assert の多くはこの不具合の再発止め)
- firmware は C の写しなので、**C と同じ所で確保し、同じ順で根を書き換えれば、同じ 2 つの守りがそのまま効く。** 足りないのは arena の仕組みだけ

### 3.3 候補

| 案 | 中身 | 良い所 | 悪い所 | 判定 |
|---|---|---|---|---|
| **A. arena と `mrb_vm_exec` の活性化を写す** | 回路が `ai` を C と同じ所で save / restore。firmware のフレームは C の関数のフレームで、その中の命令では restore しない。firmware から Ruby を呼ぶ所 (C の `mrb_funcall`) で新しい活性化 | C と同じ不変条件。firmware の書き直しが要らない。gc.rb の arena の assert (GETIDX、ENTER ほか 14 本) がそのまま物差しになる | firmware が C と違う順で書いた所は守られない。firmware の命令が作る一時の物で arena が C より伸びる (D83) | **選ぶ** |
| B. firmware のフレームが ci に無い時だけ GC | 確保の所で firmware のフレームが積まれていれば GC を延ばす | Integer を見なくてよい | 起動の `__fpga_boot` と `__fpga_run` がいつも一番下にある (§1.4)。firmware からの callback (sort のブロック、`__fpga_sendv`) の中でも GC できない。GC の時期が C と違う | 捨てる (一度も GC できない) |
| C. firmware の値を mrb_value で持つ | 物の番地を `__fpga_obj` の値でレジスタに置き、primitive も値を受ける | GC が firmware のレジスタを正確に辿れる | firmware 約 17,000 行の書き直し。可変長の番地 (中身の buffer) は Integer のまま残るので、全部は守れない。C より保守的で写しから離れる | 捨てる |
| D. firmware のフレームを保守的に走査 | firmware のレジスタの Integer が heap page の枠を指していれば印を付ける | 変更が小さい | 86921ce の「保守的なスタックの根」と同じで、gc.c に無い自前の設計。buffer の番地は守れない | 捨てる (検査の道具にだけ使う、§3.6) |
| E. GC を ref (CRuby) で走らせる | GC を回路の機能にする | 速い | 設計 §1 の分け方 (gc.c は firmware) に反する。回路の資源を食う | 捨てる |

**A を選ぶ理由:**
- C が C の局所変数を守るやり方そのものを写す (設計しない、写す)
- firmware は C の写しなので、C が守っている所は firmware でも守られる。守られない所 (写しの順の違い) は、C でも不具合になる種類で、stress で見つけられる (§9)
- mruby 自身の GC の不具合の再発止め (test/t/gc.rb の 25 本) が、この仕組みの正しさを直接測る

### 3.4 回路の規則 (ref に書く。V3 の回路も同じ)

「firmware のフレーム」は、ci の Proc が像の中 (`proc < heap_start`、D41 と同じ見方) のフレームを言う。罠のフレーム (D10、CONT_* が NONE 以外) も firmware のフレーム。

| 規則 | 何をするか | 写し元 |
|---|---|---|
| R1 活性化の始まり | firmware のフレームから像の外の Proc を呼ぶ時 (`__fpga_sendv` / `__fpga_invoke` / `__fpga_run`、firmware の中の SEND が Ruby のメソッドに当たった時) は、呼ばれるフレームの cci を `CINFO_DIRECT` にし、延長の語 `CI_AI` に今の `arena_idx` を置く (D82)。回路のレジスタ `ai` をそれにする | `mrb_funcall_with_block` の save、`mrb_vm_exec` の入口の `ai` |
| R2 命令の restore | 像の外のフレームで、ops.tsv の arena の列に restore がある命令を終えた時、`arena_idx = ai`。罠で終えた命令は罠から戻った所で同じにする。**firmware のフレームの中の命令では restore しない** (C の関数の中に restore は無い) | vm.c の各 `CASE` の `mrb_gc_arena_restore(mrb, ai)` |
| R3 C の関数の後 | 像の外のフレームが呼んだ firmware の**メソッド** (CONT_NONE) が戻った時、値を R[a] に書いてから `mrb_gc_arena_shrink(ai)`。罠のフレームが戻った時は R3 でなく R2 (その命令の restore だけ) | vm.c `L_SENDB` の cfunc epilogue (3852) |
| R4 活性化の終わり | cci が `CINFO_DIRECT` のフレームが firmware のフレームへ戻る時、`arena_idx = CI_AI` にしてから戻り値を `mrb_gc_protect`。`ai` は下の活性化のものに戻す | vm.c L_RETURN の `acc == CINFO_DIRECT` の restore、`mrb_funcall_with_block` の restore と protect |
| R5 例外の巻き戻し | `__fpga_unwind` / `__fpga_unwind_ret` で着いたフレームの活性化の `ai` に `arena_idx` を戻し、回路の `ai` を付け直す | `mrb_vm_exec` の `RETRY_TRY_BLOCK` の restore、`MRB_THROW` で C へ抜ける所 |
| R6 回路が確保する時 | 回路 (ref の Ruby の局所変数) が物の値を持ったまま確保してはいけない。値はスタックか ci か arena に置いてから確保する | vm.c の `OP_ENTER` の直し (gc.rb「OP_ENTER keeps the block alive」) |

- `ai` は回路のレジスタ (ref の `@ai`、ref_test の `CRUBY_STATE` に足す)。正本は記憶の中の `CI_AI` で、`@ai` は巻き戻しの後に一番近い DIRECT のフレームから読み直す
- firmware のメソッドから firmware のメソッドを呼ぶのは C の関数の直接の呼び出しで、arena に何もしない

### 3.5 firmware の側の関所

- **C の関数が arena を触る所は firmware も同じく触る。** 写し元の C の関数の本文に次のどれかがあれば、firmware の def にも対応する呼び出しが要る。
  firmware_test が数で確かめる (S6-0 で「足りない一覧」を commit し、S6-3 / S6-4 / S6-6 で空にする):
  - `mrb_gc_arena_save` / `mrb_gc_arena_restore`
  - `mrb_gc_protect`、`mrb_gc_register` / `mrb_gc_unregister`
  - `mrb_field_write_barrier` (`_value` も)、`mrb_write_barrier`
  - `mrb_free` / `mrb_realloc`
- **GC の中では確保しない。** gc.rb の def の irep に物を作る命令 (ARRAY 系、STRING、HASH、LAMBDA / BLOCK / METHOD、RANGE、STRCAT、INTERN) があれば、firmware_test が fail にする。
  ref は `collecting` の間の確保を `Ref::Error` にする。C には RData の dfree の中の確保があり得るが、firmware に RData は無いので、確保は不具合の印
- `__fpga_alloc` と `__fpga_slot` は S6-2 で無くす (firmware_test: 名前が 0 か所)

### 3.6 危険の分析: レジスタの Integer が動いた / 解放された物を指す

mruby の GC は物を動かさない。動くのは estalloc の `est_realloc` の中身 (ALLOC_AND_COPY) だけ。危ないのは次の型:

| 型 | 例 | C では | firmware での手当て | 見つけ方 |
|---|---|---|---|---|
| (a) 作ったばかりの物を Integer で持つ | `o = mrb_obj_alloc(...)` の後に別の確保 | arena | R1〜R4 と `mrb_obj_alloc_core` の `gc_protect` | gc.rb の arena の assert、stress |
| (b) 前からある物を、根から外した後も Integer で使う | 配列から pop した要素、表から消した行の値 | C も同じ危険。写し元は `mrb_gc_protect` か順で守る | 写し元と同じ順と protect (§3.5 の関所) | stress (N = 1)、解放した枠を埋める (D87)、独立の到達の検査 (§9.4) |
| (c) 中身の buffer の番地を持ったまま同じ物を伸ばす | `ptr = ld32(ary + A_PTR)` の後に push | C も読み直す (`ARY_PTR`) | 写し元どおり読み直す | stress の estalloc の埋め (D87) |
| (d) 罠の続きの語が値を持つ | CI_CA / CN / CSYM / CRET / CDST | — | 数と symbol だけで物を持たない (D11)。S6-0 で layout の注釈に「物を持たない」と書き、ref_test で確かめる | ref_test |
| (e) 回路が CRuby の局所変数で値を持って確保 | ref の `enter` の `regs` と `blk`、`alloc_array` の `values`、`ary_append` | vm.c は OP_ENTER で直した | R6。値がスタックに残っている間に確保する。確保する回路の命令の一覧 (ARRAY 系、ENTER の rest、ARYCAT、ARYPUSH、`run_irep`、cipop の `env_unshare`) を ref の頭に書く | gc.rb の OP_ENTER の assert、stress |
| (f) method cache と decode の cache | クラスが解放され、枠が別のクラスに使い回される | `obj_free` の `mrb_mc_clear_by_class` | 回路の method cache を消す (D90)。decode の cache (`@iseq_cache`) は iseq が像の中なので影響無し。V4 で `.mrb` を pool に読むようになったら irep の解放で消す | stress、programs |
| (g) スタックの上の方 | `mark_context_stack` が top の ci の `stack + nregs` から上を nil で消す | 同じ | firmware のフレームの nregs は firmware の irep の値で、C の cfunc より大きい (多く印を付ける)。罠の窓 (D11) は罠のフレームの中 | ref_test (罠の窓の位置) |
| (h) 例外が活性化をまたぐ | firmware の rescue で止まる、`__fpga_unwind` | MRB_TRY / MRB_CATCH と `ai` | R5 | exceptions の program と exception.rb を stress で |

**firmware のフレームの Integer の診断 (検査の道具、意味は変えない):** ref の stress の中で、sweep が解放する枠の番地と同じ Integer が firmware のフレームのレジスタにあれば、{Proc の名前、レジスタ、tt} を記録する。
死んだ局所変数 (前の周回の値) も拾うので、fail にはせず、stress で出力が host と違った時の手掛かりにする (案 D の使い道)。

## 4. 止まる GC か incremental か: 順の決定

- **決める:** GC の本体 (gc.c の状態機械、gray stack と溢れた時の走査、final_marking_phase、sweep、write barrier の中身) は S6-4 で全部写す。
  駆動だけを `run_incremental(..., run_to_root = TRUE)` にする (D20)。S6-6 で `incremental_gc_step` の上限と barrier を呼ぶ所の全部を入れて D20 / D22 / D23 を消し、S6-7 で generational を写して D21 を消す
- **理由:**
  - 1 周で終える駆動では、変更の側 (mutator) が走る時はいつも state が ROOT で、生きている物は全部白い。`mrb_field_write_barrier` / `mrb_write_barrier` は黒い物を見ないと何もしないので、中身を写しても働かない。
    だから中身は最初から写してよく、D22 (中は空) は要らない
  - barrier を呼ぶ所は回路 (ref) の命令にもある (SETIV、SETUPVAR、env_unshare、DEF、配列の push)。ref は V3 の回路の仕様なので、V3 の前 (S6 の中) に決める。V3e に回すと、V3 の回路をもう一度開けることになる
  - 1 周で終える段を先に置くのは、根と sweep の誤りと、barrier の抜けを分けて見つけるため。S6-4 で green になってから S6-6 で上限を入れれば、そこで出た違いは barrier の抜けか incremental の状態の扱いに絞られる
- **戻る道:** S6-6 / S6-7 が S6 の中で収まらない時は、D20 / D21 の行を「予定 V3e」のまま残して S7 へ進む (記録に書く)。V3 に入る条件 (計画本体) は変えない

## 5. 確保の速い道 (回路、ref.rb) と罠、負債、arena

### 5.1 回路がすること (設計 §6 の「確保」の行を具体に)

`mrb_obj_alloc_core` の後ろ半分 (freelist から外す所) だけを回路が持つ。記憶の中の `mrb_gc` を読み書きする (S2b の決まり: 状態は記憶に)。

1. `gc_debt += 1`。stress の数を数える (D87)
2. 次のどれかなら罠 `__fpga_trap_obj_alloc(tt, cls)` (firmware の `mrb_obj_alloc_core` の全部の写し):
   - 1 の後で `gc_debt > 0`
   - `free_heaps == 0`
   - `arena_idx >= arena_capa` (gc_arena_keep の realloc)
   - stress の数が N に達した
3. `p = free_heaps->freelist`、`free_heaps->freelist = p->next`、空なら `free_heaps = free_heaps->free_next`
4. `live += 1`、`arena[arena_idx++] = p`
5. 枠 64 バイトを 0 で埋め、`tt` と `c` と色 (`current_white_part`) を書く。OBJECT なら `MRB_FL_OBJ_SHAPED`
   (layout に形の flag の欄が無ければ D04 の行で扱う。S6-0 で確かめる)

- 罠に落ちた時は、firmware が 1 から全部やり直さない。回路は 1 の加算を戻してから罠にする (firmware の写しが `gc_debt++` から始まるので、二重に数えない)。
  ref_test で「罠に落ちた確保の後の gc_debt が C の式と同じ」を確かめる
- firmware が物を作る所は primitive `__fpga_obj_alloc(tt, cls)` (回路の速い道。落ちたら上の罠)。
  型の検査 (`mrb_obj_alloc` の前半) は firmware の def で、その後に primitive を呼ぶ
- **可変長:** estalloc (`est_malloc`) は S6 では firmware だけが持つ。可変長が要る回路の命令は、その命令ごと罠にして firmware が vm.c の写しで実行する。
  ARRAY / ARRAY2 (要素が 1 つ以上)、ENTER (rest が空でない)、ARYCAT、ARYPUSH (容量を越える)、RETURN 系 (cipop で env を閉じる時)。
  回路に TLSF を持たせるかは V3 で測って決める (設計 §9 に候補として書く)
- **負債の勘定:** `gc_debt` は枠の確保で +1、`incremental_gc_step` の仕事で減り、1 周の終わりに `-credit` (`incremental_gc_run`、`mrb_full_gc` の式)。
  `malloc_increase` は `mrb_realloc_simple` の中 (firmware) だけで数える

## 6. estalloc の写しと Fiddle の検査

- **1 つの source:** `fpga/firmware/estalloc.rb` (mruby ソースコード、`# C: estalloc.c <関数>`)。firmware の像に入り、ref の上で走る
- **CRuby でも同じ file を読む:** `tools/fpga/v2/est_host.rb` (Ruby コード) は、`__fpga_ld8` / `st8` / `ld32` / `st32` / `and` / `or` / `xor` / `shl` / `shr` を持つ
  名前空間の中で estalloc.rb を読む (`Module.new` の `module_eval` で、`class Object` は名前空間の中の新しいクラスになる)。記憶は binary の String。
  使う所は 2 つ:
  1. image.rb が pool を作る (§7)
  2. estalloc_test が C と比べる
- **比べ方** (`tools/fpga/v2/estalloc_test.rb`、`rake test:fpga` に入れる):
  - estalloc.c を `cc -shared -fPIC -O0 -DESTALLOC_ALIGNMENT=8` で一時の dir に build し、Fiddle で `est_init` / `est_malloc` / `est_calloc` / `est_realloc` / `est_free` / `est_permalloc` / `est_usable_size` / `est_take_statistics` を呼ぶ
  - 同じ操作の列を est_host (32bit の形) に与える。操作の列は seed つきの乱数で、次の形を混ぜる:
    - 大きさ 0〜300 が多く、ときどき 1〜70,000
    - realloc は伸ばすと縮める。free は生きているものから選ぶ
    - permalloc は少し
    - pool が尽きて NULL になる所まで回す列も入れる
  - **比べるもの:** 各操作の戻りを `BPOOL_TOP` からの差 (NULL は nil)、`est_usable_size`、`est_take_statistics` の 5 つ (total、used、free、max_free、frag)
  - C の pool の大きさを P とすると、est_host の pool は `P - POOL_HEADER_SIZE(64bit) + POOL_HEADER_SIZE(32bit)` にして、使える領域の大きさをそろえる
  - ref の上の firmware も短い列 (200 操作) で est_host と比べる。C、CRuby、ref の 3 者が一致すること
- **32bit と 64bit の違い (D25 を書き直す):**
  - 64bit の CRuby は 32bit の .so を読めない。この環境の gcc には `-m32` が無い (確かめた)
  - 違いは次の 3 つ:
    - `FREE_BLOCK` の大きさ (64bit は 32、32bit は 16)
    - `top_adrs` の位置 (block の終わりから 8 と 4)
    - `POOL_HEADER_SIZE`
  - `USED_BLOCK` はどちらも 8、`ESTALLOC_IGNORE_LSBS` と最小のブロックはどちらも 32 (ALIGNMENT 8)
  - なので `calc_index` と分割と結合の判断は同じで、戻りの番地は BPOOL_TOP からの差で一致するはず。一致しない列が出たら、この議論が誤りなので段を止める
  - 見られないのは `-m32` の build そのもので、upstream の `make test_8_24_32bit` に任せる
- **写さないもの:** `ESTALLOC_DEBUG` の検査 (解放のたびの heap の走査、二重の free の検出)。組み込みの build は DEBUG 無し。
  stress の時の埋め (0xaa / 0xff) だけは D87 で入れる

## 7. 像 (image.rb) の変更

| 置き場 | 中身 | 理由 |
|---|---|---|
| 像 (ROM、`heap_start` より前) | `mrb_state` (IMG)、シンボル表 (D07)、firmware の irep (`MRB_IREP_STATIC`)、ROM のメソッド表の層、firmware の Proc (見出しの色 RED = 7、D80)、primitive の表、programs と mrblib の `.mrb` のバイト列、VM のスタックと ci の並びと `mrb_context` (D81) | 書き換わらない物、または C でも固定の物。RED は gc.c の「Static (ROM object)」、ROM の層は `mt_readonly_p` で辿らない |
| pool (`heap_start`〜`heap_end`、estalloc) | est_init の見出し、`gc.arena` (100 語、`mrb_gc_init`)、heap page (`add_heap`)、組み込みのクラスと top_self の枠 (heap page の中)、その実行時のメソッド表と iv 表、globals の表、bop の表、`gray_stack` 以外の `mrb_gc` の malloc の物 | 実行時に realloc / free される。C では `mrb_open` がヒープに作る |

- **image.rb がすること:**
  - est_host で `est_init` と `est_malloc` を呼んで pool を並べる
  - heap page は Ruby コードの小さな写しで作る (`# C: src/gc.c add_heap` / `init_heap_page` / `link_heap_page` / `mrb_obj_alloc_core` の freelist の所)。
    firmware の gc.rb は primitive に頼るので CRuby で読まない
  - image_test は heap page を歩き、次を確かめる:
    - 各枠の tt が FREE か有効な型
    - freelist の長さ + 使っている枠 = 128
    - `live` が使っている枠の数
- `mrb_state` の `gc` の欄は、`mrb_gc` (gc.h) の順に語を置き直す (IMG の番号を付け直す)。S7 と並ぶので、S6-0 で `mrb_task_state` (queues[4]、tick、wakeup_tick、switching、main_task、scheduler_lock ほか mruby.h の順) の語も一緒に取っておく。S7 が番号を付け直さずに済むように
- 像が作る物は GC が始まる前の確保で、負債を数えない (D85)。`live` は像が作った枠の数から始める
- 小さいヒープの像は `heap_end` を `heap_start + pool の大きさ` にする (image の引数。環境変数にはしない)

## 8. task の scheduler (S7 との境)

- root_scan_phase と final_marking_phase は `mrb_task_mark_all` を呼ぶ (`MRB_USE_TASK_SCHEDULER`)。S6-4 は task.c の `mrb_task_mark_all` のうち、次の所までを写す:
  - main_task が NULL
  - queues[0..3] が全部 NULL なら早く return する
  - S6 には task が無いので、この写しで正しい
- S7 が mruby-task を写す時に、残り (各 task の `mrb_context` の stack と ci の印) を同じ def に足す。**S7 の完了の条件に「task を使う programs を stress (N = 1) で」を入れる** (計画本体の S7 の節に S7 の担当が足す)
- `execute_task` (task.c) の arena の save / restore (`mrb_protect_error` の前後) は §3.5 の関所で S7 が写す。task の切り替えは `mrb->c` を替えるので、R1〜R5 の `ai` は活性化の ci ごとに持つ形 (CI_AI) で足りる
- `GC.scheduler_driven` と `debt_limit` (mruby-task の src/gc.c、D24) と `mrb_gc_step` は S7 の範囲

### 9.2 stress の N と範囲

- **1 回の GC の重さの見積り:** 起動の後に生きている枠は約 400、pool の中の表の行は数千。gc.rb (firmware) の印と sweep で 1 回 5 万〜10 万命令 (ref で 0.4〜0.8 秒) と見る。
  スタックの nil の埋め (65,536 値) は primitive `__fpga_fill` で 1 命令にする (D81)。**S6-5 の最初に、起動の直後の `GC.start` の命令の数 C_gc を測って、この表の N を決め直す**
- **N の決め方:** 回す集合の確保の数を E (枠と realloc の合計、stat で数える)、許す時間を B 秒、ref の速さを V 命令/秒とする。
  N を `E × C_gc / N ≤ B × V` を満たす一番小さい 2 の冪にする。ref が速くなったら N を小さくする (記録に書く)

| 集合 | N (見込み) | B | E の見込み | 中身 |
|---|---|---|---|---|
| 起動 (programs の前の起動だけ) | 1 (C の MRB_GC_STRESS と同じ) | 15 分 | 約 1,500 | 空のプログラム 1 本。firmware の loader、クラスの定義、mrblib の読み込みの全部 |
| programs 9 本 (起動の後から) | 1 | 30 分 | 計 約 3,000 | 全部 |
| fuzz | 16 | 60 分 | seed 1 の 100 本で 約 20,000 | seed 1 |
| accept の一部 | 64〜256 (file ごとに式で) | 60 分 | file ごとに stat で測る | gc、hash、string、exception、proc、bs_block、class、module、methods、symbol、range。array は深い join (step の上限 3B) があるので外す |
| incremental の stress (S6-6) | 確保ごとに 1 step (上限 `step_limit` 16) | 60 分 | 同じ | programs 9 本と fuzz seed 1 |

- stress の像は `gc_stress` の語 (D87) を立てる。ref は `Ref.new(image, ...)` の引数で受ける。
  入口は `rake fpga:v2:stress` (programs と起動) と、`fpga:v2:fuzz` / `fpga:v2:accept` の引数。環境変数にはしない
- stress の時は gc.c の `MRB_GC_STRESS` と `MRB_DEBUG` の道も写して入れる:
  - 解放した枠を -1 で埋めて白くする (`obj_free` の末尾)
  - `add_gray_list` の tt の検査
  - estalloc の 0xaa / 0xff の埋め (D87)
  - 解放した物を使うと、番地が 0xFFFFFFFF になって ref が `Error` で止まる

### 9.3 小さいヒープ

- **普通:** pool は像の後ろ全部 (約 30 MB)。GC は負債で走る (`GC_STEP_SIZE` 1024 が credit の下限なので、1,000 個ほど確保するたびに 1 周)
- **小さい:** pool 1 MiB (板の R2P2 の 2,000 KB より小さく、heap page を足す道と `mrb_full_gc` で取り戻す道を踏ませる)。
  1 MiB で NoMemoryError になる file は、2 MiB で回して記録に書く (host も同じ HEAP_SIZE で回して比べる)
- **回す file:** accept の範囲内の全部 (S6-4 と S6-7 の完了の時)。途中の段は §9.2 の accept の一部と同じ集合
- **完了の条件:**
  - programs と fuzz seed 1 が、小さいヒープで stat `gc` > 0、`gc_freed` > 0、`heap_page_free` (空の page を返した数) ≥ 0 を表に出す
  - accept の合格の集合が、普通と小さいで同じ

### 9.4 独立の到達の検査 (gc_test、Ruby コード)

- stress の各 GC の後に、ref (CRuby) が根 (mrb_state の根の欄、arena、`mrb_context` の stack と ci、gray の無いこと) から記憶を独立に辿る。
  辿り方は layout.rb の形 (tt ごとの子) で書く
- 確かめること:
  - 辿れる物に FREE が無い
  - 使っている枠 = 辿れる物 ∪ arena から辿れる物 (1 周で終える駆動の時)
- firmware の gc.rb と同じ誤りを持たないよう、辿り方は gc.c を見ずに layout.rb の欄だけから書く。これは検査で、写しではない (乖離表に載せない)
